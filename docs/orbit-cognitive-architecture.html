1 Obiettivo del sistema

DocenteDoc AI è un sistema di supporto didattico per i docenti italiani delle scuole secondarie. La componente Orbit / Jarvis costituisce il nucleo cognitivo dell'applicazione: un orchestratore multi-agente che percepisce il contesto operativo del docente, coordina agenti intelligenti specializzati ed espone il risultato attraverso un'interfaccia adattiva.

Il sistema persegue quattro obiettivi fondamentali:

  • Supportare la pianificazione didattica (UDA, schede, attività);
  • Ridurre il carico cognitivo del docente durante l'uso;
  • Coordinare più agenti intelligenti senza conflitti;
  • Spiegare in modo trasparente cosa sta accadendo (XAI).

2 Architettura generale — Pipeline cognitiva

Il sistema è strutturato come una pipeline cognitiva a 8 stadi, ciascuno con una responsabilità atomica. Ogni stadio produce un artefatto immutabile consumato dallo stadio successivo; non esiste accoppiamento diretto tra stadi non adiacenti.

📡 patternDetector
P16 — rileva intenzione, complessità, confidence
🧠 cognitiveLoad
P17 — misura e limita il carico cognitivo
👁 attentionRouter
P18 — seleziona l'agente primario
🤝 coordinationEngine
P19 — assegna ruoli, gestisce handoff
⚙ executionEngine
P20 — esegue azioni reali con lifecycle
💬 narrativeLayer
P21 — traduce in linguaggio umano (IT)
🖥 JarvisNexus UI
Interfaccia adattiva — banner narrativo, orb animato
Principio architetturale chiave Ogni componente UI riceve dati già elaborati — non decide mai. Tutta la logica di coordinazione, attenzione ed esecuzione avviene fuori dal layer React, in moduli TypeScript puri testabili indipendentemente.

3 Componenti principali

P16

Behavior Analysis Module

Rileva l'intenzione dell'utente (explore | execute | learn | idle), stima la complessità del task e calcola la confidence dell'agente.

P17

Cognitive Load Manager

Calcola il livello di carico cognitivo corrente e limita l'intensità della UI per prevenire l'overload informativo.

P18

Attention Routing System

Assegna a ogni agente uno stato di attenzione: primary | secondary | background | suppressed. Un solo agente può essere primario per ciclo.

P19

Multi-Agent Coordination Engine

Assegna ruoli operativi agli agenti attivi, costruisce sequenze di azioni, gestisce il meccanismo di handoff tra personalità incompatibili con l'azione richiesta.

P20

Execution Engine

Trasforma AgentAction[] in side-effect reali tramite un registry di handler iniettabili. Espone un lifecycle TaskState per il monitoraggio.

P21

Narrative Layer

Prende l'azione prioritaria e la traduce in un messaggio italiano comprensibile: "Analyst: Analisi in corso…". Supporto per XAI (eXplainable AI).

4 Modello Multi-Agente

Il sistema definisce quattro personalità agentiche, ciascuna con un insieme fisso di capacità operative. Il meccanismo di handoff garantisce che le azioni vengano sempre eseguite dall'agente più adeguato, anche quando l'agente primario non è in grado di gestirle direttamente.

Personalità Capacità operative Ruolo nel sistema
Analyst analyze, plan Ispeziona il contesto, costruisce approcci strutturati prima di agire.
Executor execute Esegue azioni concrete (avvio flussi, task automation).
Mentor explain, plan Produce spiegazioni per l'utente; guida nei percorsi di apprendimento.
Observer observe Monitoraggio passivo; non produce output visibili ma alimenta il contesto futuro.

Regole di coordinazione

La funzione coordinateAgents() applica le seguenti regole in ordine di priorità:

  1. Execute: Executor diretto, oppure handoff dall'agente primario.
  2. Learn: Il Mentor produce una spiegazione; fallback all'Analyst.
  3. Explore: Tutti gli agenti non soppressi lavorano in parallelo.
  4. High complexity: Pipeline Analyst → handoff → Executor.
  5. Fallback: L'agente primario osserva silenziosamente (priority 1).

Anti-loop guard La pipeline è protetta da un meccanismo di deduplicazione chiave-ref (lastPipelineKeyRef) nel componente UserWorkspace: lo stesso set di azioni non viene mai rieseguito due volte consecutivamente, prevenendo loop da useEffect. 
// Esempio di utilizzo con lifecycle
await runExecutionPipeline(actions, {
  dispatch: storeDispatch,
  onStateChange: (state, action) => {
    if (state === 'running')  setTaskState('running');
    if (state === 'success')  setTaskState('idle');
    if (state === 'error')    setTaskState('error');
  },
});

6 Gestione del carico cognitivo

Il cognitiveLoad module calcola un punteggio aggregato a partire da: numero di agenti attivi, numero di flussi in esecuzione, complessità stimata del task e larghezza del viewport. Il risultato condiziona direttamente la presenza visiva del sistema:

LivelloCondizioneComportamento UI
low score ≤ 3 Interfaccia completa, animazioni attive.
medium score 4–6 Riduzione delle animazioni, limita agenti secondari.
high score ≥ 7 Modalità minimale, solo agente primario attivo.

7 Sicurezza e robustezza

  • Chiavi API esclusivamente server-side: tutte le chiamate AI transitano per api/ai.ts (Vercel Edge Function); nessuna chiave è esposta nel bundle client.
  • Nessuna automazione non approvata: il sistema suggerisce e coordina, ma non esegue azioni distruttive senza conferma esplicita dell'utente.
  • Anti-spam / anti-loop: dedupeActions() + ref-guard nel componente impediscono esecuzioni ripetute per lo stesso contesto.
  • Error containment: ogni handler è avvolto in un blocco try/catch; un errore su un'azione non blocca le successive.
  • GDPR: i dati degli alunni non sono mai inviati alle API AI; il modulo dataRetention.ts applica auto-delete degli artefatti AI dopo 365 giorni.

11 Considerazioni etiche

Principio guida: supporto, non sostituzione Il sistema è progettato per amplificare le capacità del docente, non per sostituire il suo giudizio professionale. Ogni output AI è etichettato e spiegato.
  • Nessuna automazione avviene senza un'azione utente esplicita iniziale.
  • Il Narrative Layer garantisce la spiegabilità di ogni azione degli agenti.
  • Il Cognitive Load Manager protegge l'utente da overload informativo involontario.
  • Nessun dato degli studenti viene utilizzato per l'addestramento di modelli AI.
  • L'architettura multi-agente evita il single point of failure e il single point of bias.
